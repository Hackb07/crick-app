# 1. Project Overview

Comprehensive cricket scoring app for shared hosting (LAMP): offline PWA scorer, PHP ingestion endpoints, MySQL schema with FKs & indexes, POTM & POTS engines, admin dashboard, conflict resolution, job control, security/RBAC, and realtime sync. Built for reliability, auditability, and multi-device scoring on resource-constrained shared hosting.

## 1.1. Core Principles

Low latency (<1s perceived), zero-friction UX (5th-grade friendly), scalable event architecture, shared-hosting-safe operations (no persistent workers), full offline scoring capability, sequence-based conflict resolution, and comprehensive audit trails.

## 1.2. Goals & Constraints

Primary goal: reliable, auditable scoring app on shared hosting (LAMP). Must handle multi-device scoring with conflict resolution. Non-goals: heavy realtime WebSockets on shared host. Constraints: limited DB connections, no persistent background workers assumed, unpredictable cron execution limits.

## 1.3. Deliverables

PWA scorer (offline-capable), PHP ingestion endpoints with sequence conflict handling, MySQL schema with FKs, indexes, and audit tables, POTM & POTS engines with normalization, admin dashboard (edits, clone, POTM/POTS overrides), security with RBAC and rate limiting, monitoring and alerting, comprehensive runbook, and test suites.

# 2. Architecture Blueprint

Event-driven architecture optimized for shared hosting: Client → Local Queue → Batch POST /api/v4/events (with seq validation) → MySQL event_store → cron recompute (chunked, resumable) → stats_cache. Supports offline-first, multi-device conflict resolution, and graceful degradation.

## 2.1. Event-Driven Data Flow

Client writes to local IndexedDB queue, batch POSTs events with client_base_seq to /api/v4/events endpoint; server validates seq, assigns server_seq, writes to events table; cron triggers stats recompute (chunked, heartbeats); stats_cache updated with last_event_at for staleness detection.

## 2.2. Data Model & Schema Hardening

Explicit tables with FKs, indexes, cascade rules, backfill strategy and migration plan. Core tables: events, matches, players, player_appearances, stats_cache, potm_decisions, pots_aggregate, jobs, admin_action_logs, player_edits, clone_links, events_suspense.

### 2.2.1. Teams & Series

teams table (team_id, name, created_at), series table (series_id, name, start_date, end_date); matches.series_id FK to series; index on matches.series_id for hot reads.

### 2.2.2. Player Appearances (canonical)

player_appearances table: appearance_id (PK), player_id (FK), match_id (FK), team_id (FK), role_tags (JSON), created_at, updated_at. Enforced FK relationships. Unique constraint (player_id, match_id, team_id). Supports common player logic - one player can appear for multiple teams in a series with separate appearance rows.

### 2.2.3. Events table (append-only)

events: numeric PK, event_uuid (CHAR(36) unique), match_id FK, appearance_id FK, client_id, client_ts, client_base_seq, assigned_server_seq (on insert), ball_index, payload_json (compact, short keys), created_at, processed_flag. Indexes on (match_id, created_at) and (appearance_id) for hot queries.

### 2.2.4. Stats Cache & last_event_at

stats_cache contains precomputed aggregates per appearance and per player (runs, wickets, strike_rate, economy_rate, balls_faced, overs_bowled). Add last_event_at DATETIME to indicate freshness; incremental updates on ingest; index last_event_at for staleness queries.

### 2.2.5. POTM / POTS tables

potm_decisions (match_id, computed_player_id, final_player_id, reason, admin_id, timestamp), pots_aggregate (series_id, player_id, total_points, consistency_bonus, rank), pots_overrides (series_id, player_id, adjusted_points, reason, admin_id), impact_events (event_id, appearance_id, impact_value, impact_type).

### 2.2.6. Audit & Edit Tables

player_edits (edit_id, match_id, appearance_id, old_value, new_value, reason, admin_id, timestamp), admin_action_logs (log_id, admin_id, action_type, resource_type, resource_id, reason, ip_address, timestamp), clone_links (clone_id, source_match_id, target_match_id, options_json, timestamp), events_suspense (orphaned events awaiting appearance_id resolution).

### 2.2.7. Jobs Table

jobs table for cron control: job_id, job_type, status, cursor (JSON progress), last_heartbeat, started_at, completed_at. Prevents overlapping recompute jobs via heartbeat checks.

## 2.3. Index Strategy

Hot-read indexes: events.appearance_id, events(match_id,created_at), stats_cache.appearance_id, stats_cache(player_id,match_id), matches.series_id, jobs(status,last_heartbeat). Keep indexes minimal to reduce write overhead. Avoid over-indexing for shared hosting.

## 2.4. FK Policies & Cascade Rules

Prefer RESTRICT for players/teams to avoid accidental mass-deletes. CASCADE for match->appearances only if desired; default to soft-delete pattern for safety. Document cascade decisions in schema_policy.md. Test FK constraints in migration.

## 2.5. Backend Logic (PHP + MySQL)

Endpoints: /api/v4/events (POST with client_base_seq, returns 409 if stale), /api/v4/events/sync-status (GET latest server_seq), /api/v4/matches/{id}/summary (GET with stats_cache), /api/v4/matches/{id}/finalize (POST with match state machine guards), /api/v4/admin/* (role-protected). Each uses prepared statements, validates UUID, ensures appearance_id integrity, rate limits.

### 2.5.1. Common Player Logic

When assigning same player to both teams in a match, system warns and auto-creates separate appearance_id entries (one per team). All events reference appearance_id. Stats computed per appearance, then aggregated per player_id for series totals and POTS.

### 2.5.2. Mid-Match Edits

Admins/scorers with 'senior_scorer' role can change player assignments mid-match. Edits recorded in player_edits table with reason required. Mark affected stats_cache dirty for recompute. Audit trail logged.

### 2.5.3. Clone Match Logic

Clone previous match: copy teams, appearances, and metadata but assign new match_id. Allow toss_override. Default clean clone (no events); admin flag to include_edits. Stored in clone_links table. Cross-team players handled by new appearance rows per team.

## 2.6. Performance Strategy

Batch inserts (<=10 events), indexed lookups, compact payloads. Expected 0.2-1.0s perceived latency. Designed for 6 concurrent matches, 3 scorers each on mid-tier shared host. Use persistent PDO connections, semaphore gating for heavy recomputes.

# 3. Multi-Device & Conflict Resolution

Sequence-based optimistic concurrency for multi-device scoring with idempotency guarantees, soft locks for high-impact operations, conflict markers for manual reconciliation, and 409-diff flow for stale client sync.

## 3.1. Event Model Fields

event_uuid (client-generated), client_id (device ID), client_ts (client timestamp), client_base_seq (last known server_seq from this client), assigned_server_seq (server-assigned on insert), appearance_id, ball_index, payload_json. Server validates client_base_seq matches current last_seq for the match.

## 3.2. Server seq / Conflict Flow

matches.last_seq maintained as auto-increment counter. POST /api/v4/events includes client_base_seq in header. If stale (last_seq > client_base_seq), return 409 with JSON diff of missing events. Client merges or presents conflict UI for manual resolution. Conflict events flagged with conflict_flag for admin review.

## 3.3. Soft-locks for High-impact Operations

match_locks table for actions: finalize_over, finalize_match, substitute. TTL-based locks (expires_at) to avoid deadlocks. Check before operation, acquire lock (INSERT or UPDATE), release on completion. Heartbeat during long operations.

## 3.4. Conflict Marking & Admin Reconciliation

conflicting events flagged with conflict_flag and stored in both variants. Admin panel shows both variants with timestamps and allows authoritative selection with reason logged. Recompute triggered on resolution.

# 4. Cron Cadence, Job Control & Recompute Safety

Recommended cron frequencies for shared hosting with job heartbeats and overlap prevention. Chunked recompute with resumability via cursor. Safe patterns to avoid DB connection exhaustion.

## 4.1. Frequencies (Recommended)

Immediate write for events (sync on POST). Incremental stats recompute: every 30s (aim) or 60s if provider limits. Series aggregates: every 5 minutes. Nightly full reindex. Adaptive based on hosting limits.

## 4.2. Job Table & Heartbeats

jobs table with cursor JSON, last_heartbeat, status (pending/running/completed/failed). Use MySQL GET_LOCK or job claim (UPDATE ... WHERE status='pending') to prevent overlap. Heartbeat every 10s during recompute. Detect stale heartbeats (>60s old) and reclaim.

## 4.3. Chunked Recompute & Resumability

Split recompute into small chunks (per-appearance or batch of N appearances) with progress saved in job.cursor JSON. Example cursor: {"last_appearance_id":123,"progress":"0.67"}. Long-running jobs resume from cursor rather than restart if heartbeat stale.

## 4.4. If Recompute > Cron Interval

Cron will see running job (fresh heartbeat <60s) and skip. If heartbeat stale (>60s old), reclaim and resume from cursor on next run. Ensures progress isn't lost and no infinite loops from overlapping runs.

# 5. DB Connection & Timeouts (Shared-hosting)

Persistent PDO connections with limited concurrency, semaphores for heavy jobs, per-query timeouts, batch inserts to reduce connection churn. Optimized for shared hosting connection limits.

## 5.1. PDO Config

ATTR_PERSISTENT=true, ATTR_TIMEOUT small (3-5s), ERRMODE_EXCEPTION. Use connection pooling carefully (some hosts restrict). Monitor connection count.

## 5.2. Connection Gate for Recompute

Use semaphore table (semaphores: resource_name, locked_until) or GET_LOCK for long-running recompute to limit parallel DB usage. Max 1-2 concurrent recomputes. Check before job starts.

## 5.3. Query Time Budget

Use chunked queries and SET SESSION MAX_EXECUTION_TIME where available. Detect slow-query (>3s) and bail to next chunk. Log slow queries for optimization.

# 6. Security, Auth & RBAC

JWT-based auth with role model, middleware checks, comprehensive audit logs, rate limiting with token-bucket, input validation with JSON Schema, and SQL injection/XSS prevention.

## 6.1. Roles and Permissions

super_admin (full access), admin (most ops, can override POTM/POTS), senior_scorer (can edit mid-match, clone matches), scorer (can score, limited edits), viewer (read-only). Define granular permissions for clone, override, edit players mid-match.

## 6.2. Auth Implementation

JWT tokens with role claims in payload. Endpoints validate role via middleware before processing. Admin actions require reason field and audit log entry. Token refresh on expiry.

## 6.3. Rate Limiting

Per-token/IP token-bucket stored in DB: tokens_per_minute, tokens_per_hour, bucket_size. Reject with 429 and Retry-After header. Higher quota for authorized scorer tokens (e.g., 100/min vs 10/min for anonymous).

## 6.4. Input Validation

JSON Schema validation for events: required fields, type checks, ranges (no negative runs, ball_index 1-6, max payload 2KB). Business rules: appearance_id belongs to match, ball boundaries enforced, event types enum.

## 6.5. SQL Injection & XSS Prevention

Prepared statements everywhere, parameter binding, no string concatenation in SQL. Length limits on all inputs. HTML-encode UI text in responses. Content Security Policy headers. HTTPS enforcement (redirect HTTP→HTTPS).

# 7. Frontend (Offline PWA)

Lightweight HTML/JS scorer app with IndexedDB queue, adaptive polling with SSE fallback, and full offline mode. Designed for 5th-grade-friendly UX with large buttons, visual cues, undo-first flow.

## 7.1. UI Philosophy

5th-grade friendly UX — large buttons, visual cues, undo-first flow, instant feedback, no nested menus. Optimistic UI updates before server ACK. Clear error messages. Progress indicators for sync.

## 7.2. Offline Capability

Local IndexedDB queue stores events until connection available. Automatic retry with exponential backoff (1s, 2s, 4s, 8s, max 30s). Service Worker caches static files for offline launch. Background sync API for post-online uploads.

## 7.3. Adaptive Polling / Realtime Strategy

Default: adaptive polling interval 3-15s based on activity. Uses ETag caching for low data consumption. Optional SSE gateway for push: shared-hosting backend posts diffs to lightweight SSE gateway, gateway holds long connections, reduces polling load. Fallback to polling if SSE unavailable.

### 7.3.1. SSE Gateway Pattern

Shared-hosting backend posts diffs to lightweight SSE gateway; gateway holds long connections; reduces polling load on shared host.

## 7.4. Voice & Macro Inputs (Optional)

Speech-to-text integration and one-tap macros for faster scoring. '4' macro → 'four runs' event. Voice: 'wicket' → current ball tagged as wicket. Keep simple and fast.

# 8. Statistics Engines

Handles match stats, series aggregates, POTM, and POTS logic with explicit formulas, normalization, consistency bonuses, and admin overrides with audit.

## 8.1. POTM Normalization (Explicit)

Canonical formula with overs_norm=6.0: norm_runs=(R/O)*overs_norm, norm_wk=(W/O)*overs_norm, POTM_score=wR*norm_runs + wW*norm_wk + wF*fielding + impact_bonus. Clamp O>=1/6. Default weights: wR=0.6, wW=0.8, wF=0.3 (configurable in admin).

## 8.2. Impact Events

impact_events table stores match_defining events (stumps, fielding, milestones) with impact_value used in POTM calculation. Examples: boundary (0.05), wicket (0.10), century (0.15). Aggregated per appearance for final bonus.

## 8.3. POTS — Player of the Series (Full)

Aggregate potm_points + normalized performance + consistency bonus. Configurable weights and tie-breakers. Precompute into pots_aggregate for fast reads. Steps: A) per-appearance performance_score, B) aggregate per-player in series window, C) consistency bonus (lower variance), D) weighted sum, E) rank with tie-breakers (total runs, wickets).

## 8.4. POTS Tables and Overrides

pots_aggregate (series_id, player_id, total_points, consistency_bonus, rank), pots_overrides (series_id, player_id, adjusted_points, reason, admin_id, timestamp). Admin override with audit. Incremental recompute on match completion.

## 8.5. Stats Staleness Detection & UI

stats_cache.last_event_at updated on event ingest for freshness badge. Immediate delta updates on ingest + scheduled consistency recompute to fix drift. UI shows 'live' (fresh), 'recomputing' (job running), 'stale' (needs recompute).

# 9. Clone Match Rules & Edge Cases

Default clean clone (no events), admin flag to include_edits, create new appearances per team, traceability via clone_links, cross-team player handled by new appearance rows per team. Toss override required.

## 9.1. Clone Options UI

include_edits (admin), copy_subs (preserve substitutions), copy_jersey_numbers (keep jersey numbers), toss_override (required). Warn about cross-team players and create separate appearances.

# 10. Common Player Handling

Appearance-level attribution with player_appearances; events reference appearance_id; aggregation for POTS by player_id across appearances. System auto-warns when assigning same player to both teams and creates separate appearance rows.

## 10.1. Assigning Same Player to Both Teams

System warns and auto-creates separate appearance rows (one per team). Events attach to correct appearance_id. Leaderboards can aggregate by player_id across both appearances for series totals.

# 11. Match State Machine (JSON)

Explicit state transitions: draft → scheduled → live → completed | abandoned | cancelled. Guards and actions defined. Use match_locks for guarded transitions (finalize_over, finalize_match). Illegal transitions return 400 error.

## 11.1. Over & Innings Rules

Legal vs illegal deliveries (dead ball, no ball, wide). Increment ball on legal only. Over end on 6 legal balls. Bowler per over enforced. Mid-over bowler change only for injury with admin approval (requires reason).

## 11.2. Innings Transitions

Auto-start second innings if auto_start flag set and innings1 completed (all out or all overs). Otherwise admin starts innings2. Detect chase finish (runs > target) to auto-finalize match. Manual finalization requires admin role.

# 13. Deployment & Operations

CI/CD simplified for shared hosting with manual deploys via FTP/Git, cron via provider scheduler, nightly DB backup, monitoring, alerts, and operational runbook.

## 13.1. Backup & Recovery

## 13.2. Monitoring & Alerts

Track: ingestion error rate (<1%), conflict frequency (<5%), job runtime (<60s), DB connections (<80% of limit), slow queries (>3s), rate-limit rejections (<10%). Set thresholds and alerting channels (email/SMS).

## 13.3. Migration & Rollout Plan (High Level)

Stage A: create tables/indexes with nullable fields (backward compatible), Stage B: backfill appearance_id for legacy events and populate stats_cache, Stage C: enable FKs and NOT NULL with low-traffic window. Always DB dump + rollback scripts.

## 13.4. Operational Runbook Snippets

How to handle orphan events (move to events_suspense, attempt manual resolution), reclaim stale locks (manual UPDATE where heartbeat >60s), manual recompute steps (trigger job table directly), revert a clone (delete target match), process pots_overrides (admin UI).
